# redcapmissing

<!-- badges: start -->

![Lifecycle](https://img.shields.io/badge/lifecycle-experimental-339999)

<!-- badges: end -->

`redcapmissing` constructs explicit REDCap assessment plans and
evaluates them without conflating an absent event row, an absent repeat
instance, an unstarted instrument, and a missing field value. Plans
freeze who is assessed, at which event, for which instrument, and at
which exact repeat instance.

## Installation

`redcapmissing` requires R 4.1.0 or later.

``` r
# install.packages("pak")
pak::pak("blankuzr/redcapmissing")
```

## Export REDCap records

Create a `redcapAPI::redcapConnection()` and export records. Fields
referenced by branching logic should remain in REDCap code space, and
checkbox and system columns should remain raw.

``` r
records <- redcapAPI::exportRecordsTyped(
  rcon,
  cast = list(
    radio = redcapAPI::castCode,
    dropdown = redcapAPI::castCode,
    yesno = redcapAPI::castCode,
    truefalse = redcapAPI::castCode,
    checkbox = redcapAPI::castRaw,
    system = redcapAPI::castRaw
  )
)
```

Plan construction uses physical row presence, not response content. An
exported row remains observed even when every instrument response on it
is blank.

## 1. Construct an assessment plan

Use `plan_from_data()` when observed allowable crossings are the
baseline. Its optional schedule is additive:

``` r
extended_schedule <- data.frame(
  instrument = c("labs", "labs"),
  redcap_event_name = c("month_3_arm_1", "month_3_arm_1"),
  repeat_instance = c(1L, 2L)
)

plan <- plan_from_data(
  data = records,
  rcon = rcon,
  instruments = c("demographics", "labs"),
  extended_schedule = extended_schedule
)
```

Assessible targets are the rcon-allowable crossings that are either
physically observed in `records` or generated by `extended_schedule`. An
omitted extension row does not suppress an observed target. Each
extension is expanded across records observed in the applicable arm; in
classic projects it is expanded across all observed records.

Use `plan_explicit()` when the schedule is the complete authority:

``` r
explicit_schedule <- data.frame(
  record_id = c("101", "101", "102"),
  instrument = c("demographics", "labs", "demographics"),
  redcap_event_name = c(
    "baseline_arm_1", "month_3_arm_1", "baseline_arm_1"
  ),
  repeat_instance = c(NA_integer_, 2L, NA_integer_)
)

plan <- plan_explicit(
  data = records,
  rcon = rcon,
  instruments = c("demographics", "labs"),
  explicit_schedule = explicit_schedule
)
```

Each explicit row creates only that exact target. Observed rows omitted
from the schedule are not assessed, and a scheduled record may be absent
from `records`. The absent physical row will then fail the appropriate
gate when the plan runs.

Both constructors return a compact `redcapmissing_plan` containing
canonical Assessible targets and a deterministic project-structure
fingerprint. They do not retain records or a live connection.

## 2. Run the plan

``` r
report <- run_plan(
  plan = plan,
  data = records,
  rcon = rcon,
  required_fields = TRUE,
  ignore_fields = NULL,
  exclude_types = "descriptive",
  details = FALSE
)
```

The runner evaluates four gated checks in order:

1.  `event-row-started`
2.  `repeat-instance-row-started`
3.  `instrument-started`
4.  `field-complete`

Classic event gates and regular repeat gates are not applicable. A
failed physical-row gate makes downstream checks not reached.
Instrument-started uses all usable data-entry fields on the instrument,
independently of field policy. `required_fields`, `exclude_types`, and
`ignore_fields` affect only field-complete checks, in that order. If
policy leaves no assessible fields, field completeness is not
applicable; it is never counted as an automatic pass.

A newer export from the same unchanged project may be supplied to
`run_plan()`. Planned targets stay frozen, new unplanned rows are
ignored, and absent planned rows fail their gates.

### Verified field failures

Supply `verified` and `verified_user` together to let an exact, latest
`"VERIFIED"` data-quality row resolve an otherwise-failing
field-complete result:

``` r
report <- run_plan(
  plan,
  records,
  rcon,
  verified = quality_rows,
  verified_user = "reviewer_username"
)
```

`verified` requires `project_id`, `record`, `event_id`, `field_name`,
`repeat_instrument`, `instance`, `ts`, `current_query_status`, and
`username`. Verification cannot create targets, bypass physical-row
gates, start an instrument, or restore a field removed by policy or
branching logic. The report stores audit counts, not the supplied
verification data.

## 3. Inspect results

``` r
get_summary(report)
get_missing(report, validation_check = "field-complete")
get_summary(report, instruments = "labs")

flexify(get_summary(report))
flex_event_instruments(report)
```

A `redcapmissing` result contains its plan, one `target_results` row per
Assessible target, aggregated `summary`, effective unresolved `missing`
rows, verification audit counts, ordered diagnostics, and optional
detailed rows. Structural absence is represented with typed `NA` values.

## Missing, blank, and absent values

Typed R missing values, `NaN`, empty strings, and whitespace-only
response text are missing for completeness. `Inf`, `-Inf`, and literal
strings such as `"NA"`, `"N/A"`, `"NULL"`, `"."`, and `"-999"` are not
automatically missing.

Structural values are stricter. Record IDs, event names where
applicable, and other required identifiers cannot be missing, blank,
padded, or nonfinite. Repeat instances accept positive integers,
whole-number doubles, or canonical character digits and normalize to
integer. Typed missing or blank structural values normalize to typed
`NA` only when that dimension does not apply.

An absent row has argument-specific meaning:

- absent from planner data: not observed, but an extension or explicit
  schedule may still create a target;
- absent from `extended_schedule`: do not extend, but keep an allowable
  observed crossing;
- absent from `explicit_schedule`: do not assess that crossing;
- absent from runtime data: a planned physical-row gate can fail;
- absent from `verified`: no verification evidence for that field
  context.

See `vignette("redcapmissing")` and the function reference pages for
complete schemas, normalization rules, and examples covering classic,
longitudinal, and repeating projects.
